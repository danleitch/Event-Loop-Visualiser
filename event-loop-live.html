Real code, real browser. Nothing here is faked: the order you see is the order the browser ran things.

1. What order does it run in?

Edit the code if you like, then press Run. Each line is logged in the order it actually executed, then replayed step by step.

sync = call stack microtask task (timer, click, network) before paint (rAF)

Why? The whole script is one task, so both sync lines finish first. When the stack empties, the browser drains every microtask before anything else. Then the loop moves on: a frame may be painted (rAF runs just before that) and timer tasks run on a later turn. rAF and the 0ms timer can swap places between runs, which is the point: tasks and frames are scheduled by the browser, microtasks are not.

2. Block the main thread

The ring is moved by JavaScript on every frame, so it only moves when the main thread is free. Each bar is one frame; green is smooth, red is jank.

Why? Rendering, input and your JavaScript share one main thread. The loop can only paint or handle a click between tasks, so one long task, or a microtask that keeps queueing microtasks, makes the page feel frozen even though nothing crashed.

3. Where this meets Angular

  • zone.js patches setTimeout, Promise and event listeners. When a task and its microtasks finish, it tells Angular to run change detection, which is why DOM updates appear without you asking.
  • Change detection is just JavaScript on the main thread. A slow template expression or a huge list adds to the long tasks you saw above.
  • OnPush and signals shrink the work per check, so the gap between a click and the next paint stays under about 16ms.
